# Chat security boundaries

Chat is a constrained planner. It has no shell, arbitrary URL-fetch, file-read, credential-read, policy-update, payment-approval, or delivery-marking tool. Feature explanations are curated text and do not run the payment planner or buy quotes. The current contextual `/ask` path does not use an LLM. Other optional LLM helpers elsewhere in the agent service remain advisory and cannot authorize transfers.

Messages are validated as bounded text plus a conversation ID, revision, and optional routing policy. Client roles, history, hidden commands and additional authority fields are rejected. Common instruction overrides, role spoofing, credential extraction and Unicode-obfuscated overrides are refused without changing payment slots. This screen is defense in depth: fixed tools and server authorization remain the boundary even if an unfamiliar phrase passes the screen. Encoded strings are not decoded as instructions. Supplier names and provider memos remain data, never authority.

The browser cannot supply the authoritative agent decision, screening requirements, call-back requirement, cost approval, provider or fallback options. `/ui/ask` and `/ui/review` persist responses obtained directly from the configured concierge. Payment preparation resolves the selected intent against those server records and checks its current conversation revision, tenant and company. Removing conversation metadata from a browser request does not revive an old chat quote. Changing the linked company during an outstanding agent response invalidates that response. Existing payment approval, signed terms, amount caps, deadline and reconciliation gates still apply.

Local browser endpoints require loopback connections and a matching local Host header. Origin and Fetch Metadata checks reject cross-site requests; writes require JSON. Agent-facing browser calls and sign-in calls are rate limited. Responses carry a content security policy, frame restrictions and MIME protection. UI JSON is not cached and omits raw receiving-account fields. Saved conversation views also omit those fields. Existing HTML escaping remains in place; no visual layout or styling changed. Previously cached browser data is not retroactively erased.

In `LOCAL_ROUTING=1`, the router, payout server and both uAgents processes bind to `127.0.0.1`. uAgents uses the installed SDK's ASGI host constant through `local_network.py`; listener checks must be repeated when upgrading that SDK. Operational worker messages require the expected signed agent sender, an allowed tenant and a valid correlation ID, with rate and batch limits. Unknown agents cannot invoke worker tools directly.

## Verification and scope

`npm run security:test` exercises instruction overrides, role spoofing, credential requests, Unicode variants, malformed client authority, path traversal, nested account-field redaction, forged approval metadata, held and stale quotes, tenant/company isolation, Host/Origin/Fetch Metadata checks, JSON requirements, security headers and rate limits. Python tests cover read-only explanations, input limits, worker sender checks, local listener configuration and malicious provider memos. All use temporary data and mocked tools or local HTTP fixtures; no real transfers are submitted.

The `tsx` update removes the two linked esbuild development-tool advisories found in this workspace. `npm audit` reports zero known npm advisories at the time of this change. That result does not audit Python dependencies or prove absence of vulnerabilities.

This is a local demo hardening pass, not a production security certification or a promise that every possible prompt injection is prevented. Demo login displays its one-time code, and loopback endpoints trust software running on the same computer. Before production, replace demo identity with real SSO/MFA, enforce per-user/company authorization across all APIs and stores, separate service permissions, protect stored bank details, and independently assess the entire deployment. A user with filesystem access or service credentials is outside the chat threat boundary.

The design follows OWASP's [prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) and [CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): authorization stays outside language-model output, and browser protections supplement authentication rather than replace it.
